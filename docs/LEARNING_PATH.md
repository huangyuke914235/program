# 从完成的项目开始学

先让项目跑起来，再沿着一个真实事件读代码。每一步都应能通过界面、数据库状态或测试看到结果。

## 第一步：亲手走完整条链路

运行 README 的启动命令，连接工作区并创建演示数据。

操作：找到一个暂时失败的投递，打开详情，观察它如何增加尝试次数、进入重试并最终成功。然后暂停一个端点，提交新事件，再恢复端点。

完成标准：你能用自己的话解释“事件”“端点”“投递”“尝试”四个概念之间的关系，并指出它们在界面中的位置。

从 [server/types.ts](../server/types.ts) 和 [web/](../web/) 开始阅读，不需要一开始读懂所有组件。

## 第二步：理解 HTTP API 与认证

打开本地 `/api/docs`，用管理 Token 查询端点、创建端点并发布一个事件。尝试不给 Token、发送错误的 JSON、使用不存在的端点 ID，比较返回状态。

关注 [server/](../server/) 中的 API 路由与配置读取。找到认证发生的位置，解释为什么前端界面隐藏按钮不能替代服务端认证。

完成标准：能描述一次请求从输入校验到 Store 调用，再到 JSON 响应的过程。

## 第三步：看清事务与幂等

阅读 [server/store.ts](../server/store.ts)，找到提交事件时写入的表，以及事务开始、提交和回滚的位置。

实验：使用同一个 `Idempotency-Key` 连续提交两次相同事件，再保持键不变修改载荷。检查事件总数、投递数量和 API 的冲突响应。

完成标准：能解释“对重复请求返回原结果”和“阻止接收方重复执行业务”之间的边界。阅读 [tests/](../tests/) 中相关测试，指出测试保护的是哪一个业务不变量。

## 第四步：理解后台任务如何恢复

阅读 [server/worker.ts](../server/worker.ts) 和 Store 的领取/完成逻辑。画出 `pending → processing → retrying / delivered / dead` 状态变化。

实验：在有任务时停止进程，重启并等待租约到期。观察未完成任务是否继续。然后在本机启动独立 worker，理解两个进程为什么不能随意处理同一个任务。

完成标准：能解释租约令牌、过期恢复、旧结果回写校验，以及为什么网络请求不能放进数据库事务。

## 第五步：验证失败分类与签名

阅读 [架构文档的签名协议](ARCHITECTURE.md#签名协议)，用一个小接收端保存原始请求体、验证 HMAC，并分别返回 `200`、`400`、`503`。观察不同响应的处理结果。

完成标准：能解释为什么重新序列化 JSON 可能导致验签失败，为什么暂时性失败值得重试，以及为什么接收端仍然需要幂等。

阅读传输层的地址检查与超时逻辑，尝试注册一个普通私网目标，确认系统会拒绝它。

## 第六步：独立完成一个小扩展

从下面选一个完成，先写清行为，再修改代码并运行 `npm run check`：

| 扩展                       | 需要作出的工程判断                               |
| -------------------------- | ------------------------------------------------ |
| 按事件类型筛选投递         | 筛选应该发生在前端还是数据库？分页总数如何一致？ |
| 增加事件保留期限           | 哪些记录可以删除？如何避免删掉未完成的任务？     |
| 接收端幂等示例             | 如何把去重记录和业务写入放在同一个事务？         |
| 增加队列等待时长指标       | 从哪个时间点开始算？重试等待是否包含在内？       |
| 将 Store 迁移到 PostgreSQL | 如何保持原有幂等、领取和租约测试全部通过？       |

完成标准：你能演示修改前后的行为，解释一个取舍，并指出测试覆盖了哪些故障情况。

## 面试或作品集展示时怎么说

用一次实际演示串起项目：发布事件，展示暂时失败与重试，打开尝试记录，解释事务与幂等，最后说明至少一次语义和单机 SQLite 的边界。

只介绍你能定位到代码、测试或运行结果的能力。对尚未实现的多租户、跨主机调度和高吞吐目标，明确说明它们是下一步设计方向。
